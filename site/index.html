Why Rouster

Four load-bearing ideas, all in memory-safe Rust

The installed base of open-source routing suites carries C control planes where parsing and IPC paths recur as a vulnerability class. Rouster starts from a different place: the whole workspace is Rust, protocol code contains zero unsafe, and the design still speaks every wire FRR does.

Memory-safe by construction

One async binary, Tokio tasks per protocol, multi-core from day one, per-neighbor BGP parallelism, panic isolation with supervision. The no-unsafe invariant has exactly three audited kernel read-back helpers — each documented in-tree.

A typed, multi-table core

A BIRD-style typed multi-table RIB over a Linux netlink dataplane: interfaces, addresses, routes and neighbours mirrored; static routes with ECMP and non-main tables; VRFs kept out of main; SIGHUP reload.

FRR compatibility, at the edge

Unmodified FRR staticd, bgpd and ospfd attach to rousterd as their zebra over a ZAPI codec byte-pinned against the real 10.2.2 binary — captured from live exchanges.

Native source-address validation

Unique among general-purpose suites: a SAV Information Base fed from the RIB, uRPF-family rules, the SAVNET validation modes, BAR-SAV allowlists — monitor-only by default, enforced through rp_filter or nftables.

Architecture

One binary, typed tables, protocol crates on top

Native daemons own their protocols end to end; FRR daemons join as edge clients over ZAPI when you need them; SAV reads the same RIB the protocols build.

The differentiator

Source-address validation, native to the suite

No general-purpose routing suite — FRR, BIRD, or Holo — ships packet-plane source-address validation today. Rouster does: the router checks that a packet's source address could legitimately arrive on the interface it came in on, using the very state the RIB already holds.

  • ✓SAV Information Base fed from the RIB and config — source-prefix ↔ interface bindings with provenance.
  • ✓uRPF family (RFC 3704/8704) generated from RIB data, with deletion hysteresis — what SAVOP bolts onto FRR, built in.
  • ✓The four SAVNET validation modes (IBA/IBB/PBA/PBB) per the IETF capability draft.
  • ✓BAR-SAV allowlists derived from BGP AS_PATHs + ASPA + ROA (SIDRops algorithm), provenance-tracked.
  • ✓Monitor before drop — monitor-only by default; drop mode refuses without explicit opt-in. Unknown ≠ invalid.
  • ✓Two enforcement backends behind one dataplane trait: rp_filter and nftables, with per-op kernel counters.
